LogLens · Processing explained

How your PCAPNG file becomes a graph

The file stays on disk. LogLens reads it in pieces, keeps the selected decoded records in RAM, then builds the trace and graph from those records.

From “Open” to the graph

There are normally two file-reading passes.

Pass 1 finds the available channels. Pass 2 loads data for the channels you choose. The channel list does not mean all channel data is already in RAM.

  1. PASS 1 · Discover

    You select a PCAPNG file

    LogLens reads through the capture to find channel IDs and protocol types, including channels that first appear near the end.

    Example channel list: 0x8011 — Analog, 0x9011 — Analog, plus CAN and Ethernet channels.

    RAM kept after this scan: the channel list. Packet contents from the scan are temporary.

    Show source functions
    app.rs → prepare_capture_selection()
    engine.rs → discover_capture_channels()
    capture.rs → for_each_capture_packet()
  2. USER SELECTION

    You choose channels and the time source

    For example, select analog channel 0x8011 and use TECMP source time. Clicking Load Selected Channels starts the loading worker.

    Selecting fewer channels reduces the amount of decoded data retained. It still reads through the capture.

    Why control messages may still appear
    With a nonempty channel selection, TECMP control messages are retained even when their dedicated channel was not checked, so capture-wide markers remain available.
  3. PASS 2 · Read · Repeated until end of file

    Read a PCAPNG block and extract a packet

    Read section and interface information, then packet blocks. A packet supplies its raw bytes, capture timestamp, interface and link type.

    PCAPNG packet block → CapturePacket { bytes, capture time, interface, link type }

    Temporary RAM: current block, extracted packet bytes and parser objects. Several temporary copies can coexist; the entire file is not loaded as one byte array.

    What the PCAPNG reader checks
    Section byte order, interface timestamp resolution/offset, block lengths and supported block types. Unneeded block types are skipped. The PCAPNG timestamp belongs to packet capture/arrival, not necessarily signal acquisition.
  4. PARSE AND FILTER · For each packet

    Find TECMP entries and check their channels

    An Ethernet packet can contain multiple TECMP entries. Each entry has a channel, timestamp, flags and payload. Entries outside the selected channels are skipped before being normalized and retained, apart from the control-message exception.

    Outer packet→TECMP entries→Selected entries

    Non-TECMP Ethernet and supported SocketCAN packets use their own parsing path.

    How the decoder chooses the protocol

    Message type is checked first: control and status messages remain system traffic. For bus data, data type selects the CAN, CAN-FD, LIN, Ethernet or supported analog decoder.

    engine.rs → load_capture()
    protocols.rs → normalize_tecmp()
  5. NORMALIZE · For each selected entry

    Build records that the rest of LogLens can use

    A normalized record contains channel/frame identity, timestamps, decoded payload, original payload bytes and protocol metadata.

    An analog entry with 1,400 sample bytes becomes one record containing 700 samples. Some Ethernet containers also produce additional PDU records.

    This is why file size, packet count, record count and analog sample count are different quantities.

    What a normalized record contains
    NormalizedFrame: sequence, timestamp, relative time, channel, bus type, frame key, identifier, direction, payload, raw payload, TECMP metadata, analog metadata and network metadata.
  6. MEMORY DECISION · Before retaining each record

    Is the next record within the estimated memory budget?

    Yes → keep it

    Add the record to the in-memory frame list. Shared metadata avoids some repeated allocations. Read and process the next packet.

    No → stop keeping new records

    Keep the records loaded so far. Continue scanning to the end for the selected-channel catalog, but do not retain later payloads. Mark the load as partial.

    The budget is an estimate of retained capture/index storage. It is not a hard cap on total process RAM.

    What is shared, and what is copied?
    Equal network contexts are pooled, up to 4,096 distinct pooled contexts. Extracted PDUs share their parent’s TECMP metadata. Each record still owns its payload and raw payload buffers. For analog, those two buffers contain the same sample bytes separately.
  7. AFTER THE FILE SCAN

    Choose timestamps, sort and build indexes

    Apply the selected time source, sort retained records chronologically, calculate relative time and trace deltas, and build channel/frame lookup indexes.

    Relative time zero is the first retained record after timeline alignment and sorting. It is not guaranteed to be the moment you pressed “Start logging.”

    Indexes and time arrays remain in RAM. Sorting and finalization also need temporary working memory.

    What happens to incompatible source clocks?
    When source time is selected, missing or incompatible clock domains can be placed using a capture-to-source reference. Original source and capture timestamps remain in metadata. The dataset includes a warning when projection was needed.
  8. DISPLAY

    Show trace rows and construct the selected graph

    The trace reads retained records. The graph extracts values for the selected message/signal, applies graph filters and creates display points. Large analog views use bounded display data; cursor values are read from retained original samples.

    Graph caches add RAM on top of the dataset. Hiding a graph or filtering frame IDs does not automatically unload those records.

    If loading was partial: Fit can show only the retained records. It cannot retrieve later payloads that were never stored. This version does not page missing records from disk.

One analog entry → 700 timed values

Illustrative input, not a measurement from your capture. Assume voltage units, a 0.001 scale factor and a 1 ms sample period.

Input fieldExampleWhat LogLens does
Channel0x8011Keep the entry if this channel is selected.
Analog sample bytes1,400 bytesRead 2 bytes per signed INT16 sample → 700 samples.
TECMP entry timestamp3.000 sTime of the first sample, for this example’s valid source clock.
Sample period from flags1 ms = 0.001 sSpace consecutive samples by 1 ms.
Factor / unit from flags0.001 / VMultiply each signed integer by 0.001 to obtain volts.

Decode bytes into a value

03 E8→Big-endian signed INT16: 1000→1000 × 0.001 = 1.000 V

For comparison, FF 9C is signed −100, so the same factor gives −0.100 V. The 0.001 factor is specific to these example flags; it is not fixed for every analog capture.

Place each sample on the time axis

Sample time = first-sample source time + sample index × sample period
Sample index starts at 0.
Sample 1 · index 03.000 s
Sample 2 · index 13.001 s
Sample 700 · index 6993.699 s

The first-to-last sample span is 699 ms. A run of 700 samples at 1 ms represents a 700 ms sampling block; the following sample would be at 3.700 s.

Your “logging starts at 1 s, analog arrives at 3 s” example

If the first sample’s source timestamp is 3 s and the retained graph origin is 1 s, the first analog point is at 2 s on the relative axis. If the first retained record itself is at 3 s, the graph’s zero can instead be 3 s, so that point appears at 0 s.

Source time and capture time are different

If the packet is captured at 3.700 s, choosing capture time anchors its first graph sample there. The same 700 samples then run from 3.700 to 4.399 s. In this illustrative case, the whole waveform shifts by 700 ms against source-time acquisition.

Use TECMP source time for acquisition alignment. The tool does not subtract 700 ms from a valid first-sample source timestamp.

Show source functions and RAM representation

protocols.rs → parse_analog() stores the sample bytes and metadata: count, 2-byte width, period, factor and unit. The loader does not create 700 independent frame records for this one entry.

app.rs → original_analog_view_points() reads original samples to construct bounded display points for a view. analog_sample_at() reads the retained bytes to find cursor values.

For this 1,400-byte analog entry, payload + raw payload hold 2,800 bytes of sample data, before record fields, metadata, allocation capacity, indexes and graph caches.

What stays in RAM?

On disk: your PCAPNG file

The source file remains on disk. Reading it does not mean the application keeps the entire raw capture in one memory array.

Temporary: parsing work

Current block bytes, packet bytes, parsed TECMP entries and temporary decode objects. These are released as processing moves on.

Retained: selected decoded records

Payloads, original bytes, timestamps, identities and metadata. This grows as selected data is loaded. Shared metadata reduces duplication, but payload buffers still occupy memory.

Retained: indexes and time arrays

Lookup lists for channels/messages, trace deltas and timeline coordinates. These let the UI find records without decoding the PCAPNG again on every redraw.

Additional: graph caches and UI work

Signal/display points, filtered views and drawing resources. Graph cache limits help, but these allocations still add to process memory.

Example budget on a Windows PC

The current policy uses the smaller of 40% of installed RAM and 75% of available RAM, when both are reported. Available RAM means what the operating system reports as available at the time the limits are read.

min(6.4 GiB, 6.0 GiB)6.0 GiB estimated capture/index budget

Illustration of the policy, not a live reading of your PC.

This is not a 6 GiB file-size allowance or a guaranteed 6 GiB process limit. Temporary work, graph caches, the UI and an existing dataset during reload can make process memory higher. If total RAM cannot be detected, the implementation uses an 8 GiB fallback; without an available-RAM reading, only the 40% side applies.

Why a 2 GB PCAPNG can need much more RAM

  • Each stored record has metadata and lookup overhead in addition to its bytes.
  • Some payloads exist in both decoded and raw buffers.
  • One packet may produce multiple records; analog entries contain many samples.
  • Selecting all channels retains more records than loading a subset.
Measured example from this project’s verification

A 184.3 MB capture produced 2,922,727 normalized records across 44 channels. After the metadata optimization, that debug audit measured about 1.60 GB peak process footprint on the Mac test host.

One measured workload, not a universal multiplier or a Windows capacity guarantee. File size alone cannot predict whether a 2 GB capture will fit.

Which actions actually change retained memory?

ActionEffect
Load fewer channelsUsually fewer records and payloads retained.
Filter Frame IDs in the viewerChanges the displayed results; does not automatically remove loaded records from RAM.
Close a graphChanges the view; the loaded dataset remains available.
Reload with a new selectionBuilds a new dataset. The previous dataset is kept until the load result is accepted, so peak RAM may increase during reload.
Reach the retention budgetStop retaining new records and show a partial load. There is no disk-backed paging for the missing tail.
